# ▣ PART 1. 핵심 철학 (수정 금지)

LLM 코딩에서 반복되는 4가지 함정을 막는 4원칙. **모든 프롬프트와 모든 작업은 이 원칙에 위배되면 안 됩니다.**

## 원칙 1. Think Before Coding (생각하고 코딩해)

> **가정하지 말 것. 혼란을 숨기지 말 것. 트레이드오프를 드러낼 것.**

LLM은 모호한 요청을 받으면 속으로 한 가지 해석을 골라 그냥 진행하는 경향이 있다. 이걸 막는 4가지 행동:

1. **가정을 명시하라** — 확신 없으면 묻고, 확신 있으면 "X라고 가정하고 진행한다"고 말할 것. 침묵 금지.
2. **여러 해석이 있으면 모두 제시하라** — 혼자 선택해서 진행 금지.
3. **더 단순한 길이 보이면 반박(push back)하라** — 사용자가 복잡한 방법을 시켰는데 더 쉬운 길이 보이면 그냥 따라가지 말고 제안할 것.
4. **헷갈리면 멈춰라** — 무엇이 헷갈리는지 정확히 이름 붙이고 명확화 요청.

## 원칙 2. Simplicity First (단순함이 우선)

> **문제를 푸는 최소 코드. 추측성 작업 금지.**

LLM은 본능적으로 "미래에 쓸지도 모르니까"라며 코드를 부풀린다. 5가지 금지:

1. 요청하지 않은 기능 추가 금지
2. 한 번만 쓰는 코드를 추상화 금지
3. 요청하지 않은 "유연성"이나 "설정 가능성" 금지
4. 일어날 수 없는 시나리오에 대한 에러 처리 금지
5. 200줄 짠 게 50줄로 가능했으면 다시 쓸 것

**테스트 기준**: "시니어 엔지니어가 이걸 보고 '이거 너무 복잡한데?'라고 할까?" 그렇다면 단순화하라.

## 원칙 3. Surgical Changes (수술적 변경)

> **건드려야만 하는 것만 건드려라. 자기가 만든 흔적만 치워라.**

기존 코드 수정 시 4가지 금지:

1. 인접한 코드, 주석, 포맷을 "개선" 금지
2. 망가지지 않은 것을 리팩토링 금지
3. 자기 스타일이 달라도 기존 스타일에 맞출 것
4. 무관한 죽은 코드를 발견하면 **언급만 하고 삭제하지 말 것**

**고아(orphan) 처리 규칙**:
- 내가 한 변경 때문에 안 쓰이게 된 import/변수/함수는 내가 청소
- 원래부터 죽어있던 코드는 요청 없으면 손대지 말 것

**테스트 기준**: 변경된 모든 라인이 사용자 요청에 직접 연결되어야 함. "이건 왜 바뀌었지?"에 "사용자가 시켜서요"로 답할 수 없는 줄은 빼야 함.

## 원칙 4. Goal-Driven Execution (목표 주도 실행)

> **성공 기준을 정의하라. 검증될 때까지 루프를 돌려라.**

명령형(imperative) 작업을 선언형(declarative) 목표로 변환하라:

| 명령형 (약함) | 목표 주도형 (강함) |
|---|---|
| "validation 추가해" | "잘못된 입력에 대한 테스트를 먼저 짜고, 그 테스트가 통과하게 만들어" |
| "버그 고쳐" | "버그를 재현하는 테스트를 먼저 짜고, 그 테스트가 통과하게 해" |
| "리팩토링해" | "리팩토링 전후로 테스트가 모두 통과하는지 확인" |
| "작동하게 해줘" | (금지 — 검증 불가능한 약한 기준) |

여러 단계 작업이면 검증 가능한 plan을 미리 선언:

```
1. [단계] → 검증: [어떻게 통과 여부를 알 수 있는가]
2. [단계] → 검증: [...]
3. [단계] → 검증: [...]
```

## 1.5 4원칙이 막는 LLM 코딩의 4가지 함정

| 원칙 | 막는 문제 |
|---|---|
| 1. Think Before Coding | 잘못된 가정, 숨겨진 혼란, 빠진 트레이드오프 |
| 2. Simplicity First | 과잉 엔지니어링, 부풀려진 추상화, 죽은 코드 양산 |
| 3. Surgical Changes | 무관한 편집, 건드리지 말아야 할 코드를 건드림 |
| 4. Goal-Driven Execution | 검증 부재 → 끝없는 재작업 |

## 1.6 트레이드오프 노트

이 원칙들은 **속도보다 신중함**으로 편향됨. 단순한 오타 수정이나 명백한 한 줄짜리 작업에는 전체 엄격함을 적용하지 말 것. **목표는 비사소한(non-trivial) 작업에서 비싼 실수를 줄이는 것이지, 사소한 작업을 느리게 하는 것이 아님.**

# ▣ PART 2. 역할 & 워크플로우 (수정 금지)

## 2.1 역할 분담

| 주체 | 역할 |
|---|---|
| **claude.ai** | PM/설계. Claude Code에 전달할 프롬프트(.md 파일)를 작성. |
| **사용자** | Claude Code에 프롬프트 복붙 실행, 결과 스크린샷/로그 공유. |
| **Claude Code** | 실제 코드 수정 + 빌드 + git push. |

## 2.2 프롬프트 작성 6원칙

1. **모르겠으면 무조건 사용자에게 질문** (원칙 1)
2. **여러 해석이 가능하면 모두 제시 후 선택받기** (원칙 1)
3. **더 단순한 방법이 보이면 push back** (원칙 1)
4. **UI 수정이면 반드시 목업 이미지(Visualizer) 먼저 보여줄 것**
5. **작업이 여러 개면 체크리스트로 1개씩 분리해서 프롬프트 작성**
6. **큰 작업은 단계별로 나눠 프롬프트를 순차 제공** (한 번에 다 시키지 말 것)

추상적 프롬프트 금지 — 정확한 파일 위치, 함수명, element ID, 라인 번호를 명시한다.

## 2.3 프롬프트 9단계 구조 (Claude Code에 전달 시 이 순서)

```
1. 작업 전 읽어야 할 파일
2. 작업 폴더
3. 작업 규칙 (2.4 템플릿 그대로 복사)
4. 수정 전 확인 (Claude Code가 먼저 파악할 것들)
5. 현재 상태 (정확한 파일, 라인 번호)
6. 변경 요청 (구체적으로)
7. 상세 요구사항 (element ID, 함수명 명시)
8. 건드리지 않을 것 (원칙 3)
9. 검증 단계 (PASS/FAIL 체크리스트, 원칙 4)
```

## 2.4 작업 규칙 (매 프롬프트에 그대로 복사)

```
### 작업 규칙

#### 단순함 (원칙 2)
- 요청한 기능만 구현, 추측성 추가 금지
- 한 번만 쓰는 코드는 추상화하지 말 것
- 요청하지 않은 "유연성"이나 "설정 가능성" 추가 금지
- 일어날 수 없는 시나리오에 대한 에러 처리 금지

#### 수술적 변경 (원칙 3)
- 수정 요청한 것만 수정, 다른 로직은 절대 변경 금지
- 인접한 코드, 주석, 포맷 "개선" 금지
- 망가지지 않은 것 리팩토링 금지
- 기존 스타일이 다르더라도 기존 스타일에 맞출 것
- 무관한 죽은 코드 발견 시 → 언급만 하고 삭제하지 말 것
- localStorage/DB 등 기존 데이터 절대 삭제/초기화/변경 금지
- 다른 곳도 변경이 필요하면 먼저 질문하고 승인받을 것

#### 영향 범위
- 함수 수정 시 grep으로 호출처 파악 필수
- 변경된 모든 라인이 사용자 요청에 직접 연결되어야 함

#### 검증 (원칙 4)
- 하나씩 완료될 때마다 체크리스트로 보고 (누락 방지)
- 항목별 PASS/FAIL 표 형태로 결과 보고
- PASS/FAIL 받을 때까지 다음 작업 안 넘어감
- 수정 완료 후: 빌드 → git add → commit → push
- 모든 작업 완료 후 브라우저에서 결과 확인
```

## 2.5 수정 전 확인 (매 프롬프트에 그대로 복사)

```
### 수정 전 확인
1. 관련 코드 현재 상태 먼저 파악
2. grep으로 호출처/영향 범위 확인
3. 결과를 먼저 보고한 후 수정 진행
→ Claude Code가 코드 파악 없이 바로 수정하는 것 방지
```

## 2.6 검증 규칙

- 항목별 **PASS/FAIL 표** 형태로 보고 (필수)
- API 변경 시 curl 테스트 필수
- UI 변경 시 스크린샷 확인 요청
- 다중 시나리오 (예: 일반/특수 케이스) 모두 테스트
- **PASS/FAIL 받을 때까지 다음 작업 절대 안 넘어감**

명령형 → 선언형 변환 예시:
- "X 기능 추가" → "X 기능에 대한 테스트 케이스 [a, b, c]를 정의하고 모두 통과시켜라"
- "Y 화면 만들어줘" → "Y 화면에 [요소 1, 2, 3]이 [동작 A, B, C]를 한다는 걸 스크린샷으로 검증할 수 있게 만들어라"

## 2.7 워크플로우

```
claude.ai (PM/설계)
  ↓ 프롬프트 .md 작성
사용자가 Claude Code에 복붙
  ↓ Claude Code가 필수 파일 읽고 코드 수정
빌드 → git push → 자동 배포
  ↓
사용자가 프로덕션에서 최종 확인 → PASS/FAIL
  ↓ FAIL이면 추가 프롬프트, PASS면 다음 작업
```

## 2.8 Claude Code 출력 규칙

- **채팅 답변** = 복붙용 단일 코드 블록, 설명은 코드 블록 밖에
- **프롬프트는 .md 파일**로, 9단계 표준 형식 엄수
- **작업 규칙 섹션** (2.4) 매번 포함 필수
- **검증 단계** (PASS/FAIL 체크리스트) 매번 포함 필수

## 2.9 프롬프트 복잡도 기준

| 작업 규모 | 프롬프트 수준 |
|---|---|
| 단순 수정 (1-2줄) | 수정 전 확인 + 변경 + 검증 |
| 로직 변경 | 수정 전 확인 + 영향 범위 + 변경 + 건드리지 않을 것 + 검증 5개+ |
| 전면 재작성 | 전체 설계 + 상세 코드 + 건드리지 않을 것 + 검증 10개+ |

## 2.10 일반 주의사항

- curl 테스트 시 반드시 더미 키(`test_xxx`) 사용 — 실제 키 사용 금지 (데이터 손상 위험)
- 배포 후 브라우저 강제 새로고침 필수 (Cmd+Shift+R / Ctrl+Shift+R)
- git push ≠ 배포 완료 — 배포 플랫폼 대시보드에서 상태 확인 필요

⚠️ Vercel env vars 중 `$` 포함 값 → base64 인코딩 후 `_B64` 접미사로 저장.

## 3.6 동기화 아키텍처

```
사용자 입력 → localStorage 저장 → autoSyncToSupabase(key) [5초 debounce]
→ POST /api/sync/save → Supabase app_data 업데이트
→ Supabase Realtime → 다른 사용자 브라우저에 WebSocket 전달
→ realtimeDownloadAndRefresh() → localStorage 갱신 → UI 반영
```

페이지 로드 시: localStorage 캐시로 즉시 렌더링 → 백그라운드에서 Supabase 동기화.

## 3.13 프로젝트 특화 주의사항

- TTI 매칭: `mw_products.ttiNum` vs TTI productCode는 **leading zero 차이** ("018468029" vs "18468029") → 항상 `normalizeTtiCode()` 사용
- 발주탭 재고: `_poTtiStockMap[code]` 참조 (값: `'a'`=●, `'b'`=▲, `'c'`=✕). `ttiStock` 필드는 별개 — 사용 금지
- Naver 판매자상품코드 = `mw_products.code` (관리코드/manageCode 아님)
- 경영박사 ERP = **단방향 쓰기 전용** (전표 read API 없음). Supabase가 master source of truth
- Vercel webhook 미발동 시 → empty commit으로 재트리거
- CSS 복잡 탭은 `#tab-id.active` 개별 ID override 필수 (전역 `.tab-content.active`만 의존 금지)
